## Before opening a pull request

1. Read the target repository's README, licence and contribution instructions.
2. Check existing issues and pull requests before starting overlapping work.
3. Keep each change focused and describe its observable behaviour.
4. Run the repository's required checks, including its configured [Code Discipline](https://github.com/Trebired/code-discipline) gate.
5. Submit a pull request explaining what changed, why it matters and how you verified it.

Contributions are made under the receiving repository's licence. Products use AGPL-3.0; packages use MIT or AGPL-3.0. The repository's own `LICENSE` file is authoritative.

We prefer clear reports with reproduction steps over vague bug descriptions. A precise issue is a valuable contribution even without a patch.

## How we work

- **Open from the first commit.** No proprietary or source-available tier of Trebired's own software.
- **Decisions are traceable.** Review changes, issues, commits, release notes and tags in the relevant repository.
- **Published releases remain published.** Corrections arrive in new releases, not rewritten versions.
- **Forks are welcome.** Keep using the code under its licence, including if Trebired stops maintaining it.
- **The name is separate from the code.** The software licence does not grant Trebired trademark rights. See our [trademark policy](https://trebired.com/trademark).

## Security and contact

Report vulnerabilities privately to **security@trebired.com**. Do not disclose security-sensitive details in public issues.

For organization questions, see [trebired.com](https://trebired.com). For websites and software built for clients, visit **[Trebired Clients](https://github.com/Trebired-Clients)**.
